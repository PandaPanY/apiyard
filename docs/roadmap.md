# 开发路线图

> 最后更新：2026-11-03
> 工时预估按每周约 10 小时的业余时间计算，只用来排顺序和发现风险，不是承诺。每完成一个里程碑都要回头校准。

## 总览

```
M0 立项 ✅ ─▶ M0.5 前置验证 ─▶ M1 账号与分组 ─▶ M2 项目与接口 ─▶ M3 开放 API 与导入导出 ─┐
                                                                                         ├─▶ M6 打包发布 = v0.1
                                         M4 数据迁移（M2 之后可以和 M3 并行）─────────────┤
                                         M5 Mock 服务（M2 之后可以和 M3 并行）────────────┘
v0.2：M7 MCP Server        v0.3 及以后：延后功能，按用户反馈排序
```

| 里程碑 | 预估 | 累计 | 产出 |
|---|---|---|---|
| M0 立项 | — | — | ✅ 调研、架构、骨架 |
| M0.5 前置验证 | 1–2 周 | 2 周 | YApi 对照环境、前端可行性结论、兼容测试框架 |
| M1 账号与分组 | 2–3 周 | 5 周 | 能登录、管理分组和成员 |
| M2 项目与接口 | 3–4 周 | 9 周 | **界面核心流程可用** |
| M3 开放 API 与导入导出 | 1–2 周 | 11 周 | 周边工具可以接入 |
| M4 数据迁移 | 1–2 周 | 13 周 | 真实 YApi 数据可以迁移过来 |
| M5 Mock 服务 | 1–2 周 | 15 周 | 安全的 Mock |
| M6 打包发布 | 1 周 | 16 周 | **v0.1 发布** |

**调整原因**：README 里原先的 M1–M6 是按"功能模块"划分的。但前端要沿用 YApi 原有界面（决策 D4），界面直接调用的是 YApi 的内部接口，所以现在改为**按界面能用起来的顺序**、直接以 YApi 的接口为单位来划分，避免先另起一套接口、到后面再返工去兼容。完整的接口清单和每个接口所属的阶段见 [yapi-routes.md](yapi-routes.md)。

## M0.5 前置验证（1–2 周）

**目标**：在写业务代码之前，排除最大的不确定因素，并准备好兼容性测试用的"标准答案"。

| # | 任务 | 说明 |
|---|---|---|
| 1 ✅ | 搭建 YApi 1.12.0 对照实例 | 部署在局域网测试服务器（Ubuntu 24.04），用 Docker Compose 运行：自建 YApi 镜像（`node:14` + `yapi-vendor@1.12.0`）+ 官方 `mongo:4.4`。因为 YApi 有未修复的 RCE 漏洞，端口只绑定 `127.0.0.1`，通过 SSH 隧道访问。部署文件放在 `testenv/yapi/` |
| 2 ✅ | 验证预构建前端能被 Go 托管 | `yapi-vendor` 自带构建好的前端（`static/prd`）。让 Go 托管这些静态文件，并把 `/api` 请求转发给对照实例，确认界面全部功能正常 |
| 3 ✅ | 确认怎么隐藏延后的功能 | 预构建的文件改不了。可选做法：后端对延后接口返回"未开放"；由 Go 注入一小段 CSS/JS 隐藏菜单；或者用 Node 14 重新构建前端。选改动最小、又能工作的那个。**另外**：原版前端会请求 Google Analytics 和 fastmock.site（版本检查，证书已过期），内网部署会泄露使用数据，考虑由 Go 加 `Content-Security-Policy` 响应头禁止外连 |
| 4 ✅ | 兼容测试框架 | 写一个录制工具：通过对照实例调用 M1/M2 的接口，把请求和响应保存为 golden 文件。比对时忽略 ID 和时间戳这类易变字段，只比对结构和取值 |
| 5 ⏸ | 联系 ApiMind 作者 | 在 YApi issue #2806 下了解对方的进展，看能不能合作，或者明确双方的差异。**推迟到公开仓库时**：对方的帖子发布 5 个多月没有回复，也没有公开仓库 |
| 6 ✅ | 确定 SQLite 表结构草案 | 参照 YApi 的 Mongoose 模型；ID 沿用自增整数（D3） |

**验收标准**：
- 对照实例能正常运行，并预置一份示例数据（2 个分组、3 个项目、30 个以上接口）。
- 由 Go 托管前端时，界面的核心流程全部可用（这时后端还是 YApi）。
- 能一条命令录制 golden 文件，并对比任意一个服务的响应。
- 对 D4（沿用前端）做出**确认或放弃**的结论，写进 `architecture.md`。

**决策点**：如果预构建前端无法单独托管，或者隐藏功能的代价太大，就转向"重写一个精简前端"。那样 M2 会再增加 4–6 周，整个路线图都要重排。

## M1 账号与分组（2–3 周）

**目标**：用户能注册和登录，能管理分组和成员，界面首页能正常打开。

| # | 任务 | 进度 |
|---|---|---|
| 1 | 存储层：SQLite 连接与数据库版本迁移、`store` 接口、用户 / 分组 / 成员 / 关注的表 | ✅ |
| 2 | 统一的响应封装 `{errcode, errmsg, data}`，错误码与 YApi 一致 | ✅ |
| 3 | 登录会话：Cookie 名称和格式与 YApi 一致（`_yapi_token`、`_yapi_uid`），密码哈希兼容 YApi 的算法，以便迁移后原密码还能用 | ✅ 令牌与 YApi 逐字节一致 |
| 4 | 角色权限：admin / owner / dev / guest，权限判断逻辑对照 YApi 的 `checkAuth` | ✅ 分组部分；项目部分随 M2 |
| 5 | 实现 24 个接口：`/api/user/*`（14 个）、`/api/group/*`（10 个）。`/api/follow/*`（3 个）依赖项目数据，移到 M2 | ✅ 24/24；`user/project` 中项目、接口两种类型随 M2 补全 |
| 6 | 托管前端静态文件，以及前端路由的回退处理 | ✅（M0.5 完成） |
| 7 | 首次启动时创建管理员账号（命令行参数或环境变量） | ✅ |

**验收标准**：
- 24 个接口全部通过 golden 对比测试（`go test` 自动执行）。
- 在界面上完成：注册 → 登录 → 创建分组 → 添加成员 → 修改角色 → 退出。
- 存储层的单元测试覆盖率 ≥ 70%。

## M2 项目与接口（3–4 周）

**目标**：界面的核心流程可用，也就是说，**单独用 ApiYard 就能日常管理接口文档了**。

按依赖关系拆成四部分，每部分都有自己的兼容场景，可以单独验收和提交：

| 部分 | 内容 | 兼容场景 | 进度 |
|---|---|---|---|
| M2-1 | 项目增删改查、环境 / tag / 图标、token、检查项目名、搜索、项目权限；关注 3 个接口；`log/list`；`user/project` 的项目类型 | `03-project` | ✅ |
| M2-2 | 项目成员 5 个接口 | `04-project-member` | ✅ |
| M2-3 | 分类与接口 16 个接口（含 WebSocket 冲突检测、`schema2json`）；`user/project` 的接口类型；复制项目（会连同接口一起复制，所以放在接口之后） | `05-interface` | ✅ |
| M2-4 | `log/list_by_update`、4 个占位接口、`project/download` | `06-misc` | ✅ |

| # | 任务 |
|---|---|
| 1 | 表：项目、项目成员、环境、标签、分类、接口、操作日志（M0.5 已建好） |
| 2 | 接口数据的存储：常用于查询的字段单独建列，其余字段以 JSON 存储（D2） |
| 3 | `/api/project/*` 20 个接口，包括复制项目、项目 token、环境配置 |
| 4 | `/api/interface/*` 16 个接口，包括分类、排序、编辑冲突检测（`solve_conflict`）、JSON Schema 转示例（`schema2json`） |
| 5 | `/api/log/*` 2 个接口：操作动态 |
| 6 | 4 个占位接口返回"功能未开放"（LDAP 登录、第三方登录、下载浏览器插件、Swagger 地址） |
| 7 | 修改接口时检查对应的项目权限 |

**验收标准**：
- 38 个接口通过 golden 对比测试。
- 在界面上完成：创建项目 → 建分类 → 新建并编辑接口（包括 JSON Schema）→ 调整排序 → 查看动态 → 复制项目。
- 两个浏览器同时编辑同一个接口时，冲突提示正常。
- **完成后在 GitHub 公开仓库**（标注"开发中"），并把模块路径改成完整的仓库路径。

## M3 开放 API 与导入导出（1–2 周）

**目标**：现有的 YApi 周边工具直接改个地址就能接入。

和 M2 一样按依赖拆成四部分，每部分有自己的兼容场景：

| 部分 | 内容 | 兼容场景 | 进度 |
|---|---|---|---|
| M3-1 | 开放 API 鉴权：白名单接口支持 `token` 参数（新旧两种 token），token 只能操作所属项目 | `07-open-api` | ✅ |
| M3-2 | 导出：`/api/plugin/export`（JSON / Markdown / HTML）、`/api/plugin/exportSwagger` | `08-export` | ✅ |
| M3-3 | 导入：`/api/open/import_data`（Swagger 2 / OpenAPI 3 的 JSON，三种同步模式）；界面导入（Swagger、Postman、HAR、YApi JSON）实测 | `09-import` | |
| M3-4 | 生态实测：yapi-to-typescript、Yapi-MCP、easy-yapi | — | |

| # | 任务 |
|---|---|
| 1 | token 编解码：`EVP_BytesToKey(MD5)` + AES-192-CBC，兼容原始项目 token（此时 uid 视为 999999）。✅ M2-1 已提前完成 |
| 2 | 开放 API 鉴权：白名单接口支持 `token` 参数 |
| 3 | `/api/open/import_data`：通过 Swagger JSON 导入，支持普通、智能合并、完全覆盖三种模式。**不支持通过 URL 导入**（服务端代取任意 URL 有 SSRF 风险，2026-11-04 决定先不做） |
| 4 | 导出：`/api/plugin/export`（JSON / HTML / Markdown）、`/api/plugin/exportSwagger` |
| 5 | 界面导入：YApi 的导入在**浏览器里解析**文件，再调用 `add_cat`、`project/up`、`interface/add`、`interface/save` 逐条写入；`/api/interface/interUpload` 只是上传组件上声明的地址，实际不会被请求。所以这部分只需实测，不需要新接口 |
| 6 | 生态实测：yapi-to-typescript 生成代码、Yapi-MCP 读写接口、easy-yapi 上传文档 |

**验收标准**：
- token 编解码与 YApi 生成的 token 互通，双方生成的 token 都能被对方解析。
- 三个周边工具都只改服务器地址，不改其他配置，就能正常工作。
- 一份 OpenAPI 3 文件导入后再导出，主要信息不丢失（有单元测试保证）。

## M4 数据迁移（1–2 周，M2 完成后即可开始）

**目标**：一条命令就能把真实的 YApi 实例搬过来。

| # | 任务 |
|---|---|
| 1 | `apiyard migrate --mongo <uri> --passsalt <salt>`：连接 YApi 的 MongoDB 读取数据 |
| 2 | 迁移用户、分组、项目、token、分类、接口、关注；原样保留 ID（D3） |
| 3 | 迁移前预检：统计各类数据的数量；迁移后核对：逐条对比 |
| 4 | 支持重复执行（先清空目标库，或者跳过已存在的数据） |
| 5 | 迁移指南文档 |

**验收标准**：
- 迁移对照实例后：原账号密码可以登录；原 token 在周边工具里仍然可用；原有的接口链接和 Mock 地址都不失效。
- 迁移约 1 万个接口的数据，耗时少于 1 分钟。

## M5 Mock 服务（1–2 周，M2 完成后即可开始）

**目标**：Mock 地址与 YApi 一致，并且从设计上保证安全。

| # | 任务 |
|---|---|
| 1 | 路由 `/mock/{projectId}/{path}`，包括路径参数匹配和 `basepath` 处理 |
| 2 | 返回数据的来源：接口的 `res_body`；如果是 JSON Schema，就按 Schema 生成随机数据 |
| 3 | 支持 Mock.js 的常用占位符（`@string`、`@integer`、`@date` 等，按 YApi 文档列出的范围实现） |
| 4 | 跨域支持、延迟模拟、请求参数校验（可选） |
| 5 | **不执行任何脚本**：项目上已有的 Mock 脚本会被忽略，界面上给出提示 |

**验收标准**：
- 对照实例里的 Mock 地址替换成 ApiYard 的地址后，返回数据的结构一致。
- 安全测试：把 YApi 已公开的 RCE 攻击请求原样发过来，ApiYard 不会执行任何代码。

## 测试策略

| 层次 | 做法 |
|---|---|
| 单元测试 | 存储层、token 编解码、Mock 生成器、格式转换器 |
| 兼容测试 | 用 golden 文件对比 ApiYard 与 YApi 的接口响应（M0.5 搭建框架，M1 起每个接口都要覆盖） |
| 生态测试 | 用真实的周边工具跑脚本（M3 起） |
| 迁移测试 | 对照实例 → 迁移 → 逐条核对数据（M4 起） |
| 界面验收 | 每个里程碑结束时，在浏览器里手动走一遍验收流程 |

## 风险与决策点

| 风险 | 何时决定 | 应对 |
|---|---|---|
| 预构建前端无法单独使用 | M0.5 结束 | 转向重写精简前端，路线图重排 |
| YApi 的密码哈希或 Cookie 机制难以兼容 | M1 开始时 | 读源码确认；如果实在无法兼容，迁移后让用户重置密码 |
| ApiMind 先发布 | M0.5 联系后 | 在差异化上加码（单文件、SQLite、安全），或者寻求合作 |
| 业余时间不够，进度拖延 | 每个里程碑结束时 | 砍范围，不砍质量；可以把 M4、M5 推到 v0.1 之后 |
| 项目公开后被 issue 淹没 | M2 公开时 | 提供 issue 模板；README 写清楚"不做什么" |
