# 开发路线图

> 最后更新：2026-11-12
> 工时预估按每周约 10 小时的业余时间计算，只用来排顺序和发现风险，不是承诺。每完成一个里程碑都要回头校准。

## 总览

```
M0 立项 ✅ ─▶ M0.5 前置验证 ─▶ M1 账号与分组 ─▶ M2 项目与接口 ─▶ M3 开放 API 与导入导出 ─┐
                                                                                         ├─▶ M6 打包发布 = v0.1
                                         M4 数据迁移（M2 之后可以和 M3 并行）─────────────┤
                                         M5 Mock 服务（M2 之后可以和 M3 并行）────────────┘
v0.2：M7 MCP Server        v0.3 及以后：延后功能，按用户反馈排序
```

| 里程碑 | 预估 | 累计 | 产出 |
|---|---|---|---|
| M0 立项 | — | — | ✅ 调研、架构、骨架 |
| M0.5 前置验证 | 1–2 周 | 2 周 | YApi 对照环境、前端可行性结论、兼容测试框架 |
| M1 账号与分组 | 2–3 周 | 5 周 | 能登录、管理分组和成员 |
| M2 项目与接口 | 3–4 周 | 9 周 | **界面核心流程可用** |
| M3 开放 API 与导入导出 | 1–2 周 | 11 周 | 周边工具可以接入 |
| M4 数据迁移 | 1–2 周 | 13 周 | 真实 YApi 数据可以迁移过来 |
| M5 Mock 服务 | 1–2 周 | 15 周 | 安全的 Mock |
| M6 打包发布 | 1 周 | 16 周 | **v0.1 发布** ✅ 2026-11-10 |
| M7 MCP Server | 2.5–3.5 周 | — | **v0.2 发布** |

**调整原因**：README 里原先的 M1–M6 是按"功能模块"划分的。但前端要沿用 YApi 原有界面（决策 D4），界面直接调用的是 YApi 的内部接口，所以现在改为**按界面能用起来的顺序**、直接以 YApi 的接口为单位来划分，避免先另起一套接口、到后面再返工去兼容。完整的接口清单和每个接口所属的阶段见 [yapi-routes.md](yapi-routes.md)。

## M0.5 前置验证（1–2 周）

**目标**：在写业务代码之前，排除最大的不确定因素，并准备好兼容性测试用的"标准答案"。

| # | 任务 | 说明 |
|---|---|---|
| 1 ✅ | 搭建 YApi 1.12.0 对照实例 | 部署在局域网测试服务器（Ubuntu 24.04），用 Docker Compose 运行：自建 YApi 镜像（`node:14` + `yapi-vendor@1.12.0`）+ 官方 `mongo:4.4`。因为 YApi 有未修复的 RCE 漏洞，端口只绑定 `127.0.0.1`，通过 SSH 隧道访问。部署文件放在 `testenv/yapi/` |
| 2 ✅ | 验证预构建前端能被 Go 托管 | `yapi-vendor` 自带构建好的前端（`static/prd`）。让 Go 托管这些静态文件，并把 `/api` 请求转发给对照实例，确认界面全部功能正常 |
| 3 ✅ | 确认怎么隐藏延后的功能 | 预构建的文件改不了。可选做法：后端对延后接口返回"未开放"；由 Go 注入一小段 CSS/JS 隐藏菜单；或者用 Node 14 重新构建前端。选改动最小、又能工作的那个。**另外**：原版前端会请求 Google Analytics 和 fastmock.site（版本检查，证书已过期），内网部署会泄露使用数据，考虑由 Go 加 `Content-Security-Policy` 响应头禁止外连 |
| 4 ✅ | 兼容测试框架 | 写一个录制工具：通过对照实例调用 M1/M2 的接口，把请求和响应保存为 golden 文件。比对时忽略 ID 和时间戳这类易变字段，只比对结构和取值 |
| 5 ⏸ | 联系 ApiMind 作者 | 在 YApi issue #2806 下了解对方的进展，看能不能合作，或者明确双方的差异。**暂不考虑**（2026-11-09 决定）：对方的帖子发布 5 个多月没有回复，也没有公开仓库 |
| 6 ✅ | 确定 SQLite 表结构草案 | 参照 YApi 的 Mongoose 模型；ID 沿用自增整数（D3） |

**验收标准**：
- 对照实例能正常运行，并预置一份示例数据（2 个分组、3 个项目、30 个以上接口）。
- 由 Go 托管前端时，界面的核心流程全部可用（这时后端还是 YApi）。
- 能一条命令录制 golden 文件，并对比任意一个服务的响应。
- 对 D4（沿用前端）做出**确认或放弃**的结论，写进 `architecture.md`。

**决策点**：如果预构建前端无法单独托管，或者隐藏功能的代价太大，就转向"重写一个精简前端"。那样 M2 会再增加 4–6 周，整个路线图都要重排。

## M3 开放 API 与导入导出（1–2 周）

**目标**：现有的 YApi 周边工具直接改个地址就能接入。

和 M2 一样按依赖拆成四部分，每部分有自己的兼容场景：

| 部分 | 内容 | 兼容场景 | 进度 |
|---|---|---|---|
| M3-1 | 开放 API 鉴权：白名单接口支持 `token` 参数（新旧两种 token），token 只能操作所属项目 | `07-open-api` | ✅ |
| M3-2 | 导出：`/api/plugin/export`（JSON / Markdown / HTML）、`/api/plugin/exportSwagger` | `08-export` | ✅ |
| M3-3 | 导入：`/api/open/import_data`（Swagger 2 / OpenAPI 3 的 JSON，三种同步模式）；界面导入（Swagger、Postman、HAR、YApi JSON）实测 | `09-import` | ✅ |
| M3-4 | 生态实测：yapi-to-typescript、Yapi-MCP、easy-yapi（脚本见 [`testenv/eco`](../testenv/eco/README.md)） | — | ✅ |

| # | 任务 |
|---|---|
| 1 | token 编解码：`EVP_BytesToKey(MD5)` + AES-192-CBC，兼容原始项目 token（此时 uid 视为 999999）。✅ M2-1 已提前完成 |
| 2 | 开放 API 鉴权：白名单接口支持 `token` 参数 |
| 3 | `/api/open/import_data`：通过 Swagger JSON 导入，支持普通、智能合并、完全覆盖三种模式。**不支持通过 URL 导入**（服务端代取任意 URL 有 SSRF 风险，2026-11-04 决定先不做） |
| 4 | 导出：`/api/plugin/export`（JSON / HTML / Markdown）、`/api/plugin/exportSwagger` |
| 5 | 界面导入：YApi 的导入在**浏览器里解析**文件，再调用 `add_cat`、`project/up`、`interface/add`、`interface/save` 逐条写入；`/api/interface/interUpload` 只是上传组件上声明的地址，实际不会被请求。所以这部分只需实测，不需要新接口 |
| 6 | 生态实测：yapi-to-typescript 生成代码、Yapi-MCP 读写接口、easy-yapi 上传文档 |

**验收标准**：
- token 编解码与 YApi 生成的 token 互通，双方生成的 token 都能被对方解析。
- 三个周边工具都只改服务器地址，不改其他配置，就能正常工作。yapi-to-typescript、Yapi-MCP 真实运行，结果与原版一致；easy-yapi 是 IDEA 插件，只按其源码回放了请求，**真实插件尚未验证**。
- 一份 OpenAPI 3 文件导入后再导出，主要信息不丢失（有单元测试保证）。导出格式是 Swagger 2，与原版相同；导出为 OpenAPI 3 不在 M3 范围内。

## M4 数据迁移（1–2 周，M2 完成后即可开始）

**目标**：一条命令就能把真实的 YApi 实例搬过来。

| # | 任务 | 进度 |
|---|---|---|
| 1 | `apiyard migrate -mongo <uri>`：连接 YApi 的 MongoDB 读取数据。驱动支持 MongoDB 3.6 及以上；更老的版本用 `-dump` 读取 mongodump 导出的目录。passsalt 不需要在迁移时提供：数据库里存的是原始 token，启动时用 `-token-salt` 指定 | ✅ |
| 2 | 迁移用户、分组、项目、token、分类、接口、关注，以及动态和头像；原样保留 ID（D3），按 `identitycounters` 抬高 ID 序列 | ✅ |
| 3 | 迁移前预检（`-dry-run`）：统计各类数据的数量，列出会跳过和修正的记录；迁移后核对：行数一致，每条记录用 ApiYard 的读取方法读回后与源数据一致 | ✅ |
| 4 | 支持重复执行：先写临时文件，核对通过才替换目标库；目标库已存在时要加 `-overwrite` | ✅ |
| 5 | 迁移指南文档（[migration.md](migration.md)） | ✅ |

**验收标准**：
- 迁移对照实例后：原账号密码可以登录；原 token 在周边工具里仍然可用；原有的接口链接和 Mock 地址都不失效。✅ 除 Mock 地址外均已验证：`tools/migcheck` 用同样的请求遍历原版和迁移后的 ApiYard，156 个请求的响应完全一致（包括管理员原密码登录、用原 token 调用开放 API）；`testenv/eco/migrated.sh` 用原 token 运行 yapi-to-typescript，两边生成的代码逐字一致。Mock 地址随 M5 完成：兼容场景 `10-mock` 与原版一致。
- 迁移约 1 万个接口的数据，耗时少于 1 分钟。✅ 1 万个接口加 3 万条动态约 2 秒。

## M5 Mock 服务（1–2 周，M2 完成后即可开始）

**目标**：Mock 地址与 YApi 一致，并且从设计上保证安全。

| # | 任务 | 进度 |
|---|---|---|
| 1 | 路由 `/mock/{projectId}/{path}`，包括路径参数匹配和 `basepath` 处理 | ✅ 完整路径、`query_path`、`{name}` / `:name` / 段内 `{name}` 三种路径参数，与原版的匹配顺序和怪癖一致 |
| 2 | 返回数据的来源：接口的 `res_body`；如果是 JSON Schema，就按 Schema 生成随机数据 | ✅ 包括 YApi 的 `${query.x}` 请求变量和 `name\|regexp` |
| 3 | 支持 Mock.js 的常用占位符（`@string`、`@integer`、`@date` 等，按 YApi 文档列出的范围实现） | ✅ 实际移植了 Mock.js 的全部生成规则和占位符（`internal/mockjs`），与原版交叉核对 |
| 4 | 跨域支持、延迟模拟、请求参数校验（可选） | ✅ 跨域和严格模式校验；原版的延迟只能通过脚本设置，不做 |
| 5 | **不执行任何脚本**：项目上已有的 Mock 脚本会被忽略，界面上给出提示 | ✅ 界面入口在 M0.5 已隐藏，改为响应头 `X-ApiYard-Mock-Script: ignored` 和迁移报告提示 |

**验收标准**：
- 对照实例里的 Mock 地址替换成 ApiYard 的地址后，返回数据的结构一致。✅ 兼容场景 `10-mock` 共 70 次调用与原版一致（随机生成的响应比对形状）；Mock.js 的 43 组模板各生成 400 次，统计特征与原版一致。JSON Schema 的 Mock 刻意与原版不同：原版因库的缺陷字段随机缺失、数组总是空的，ApiYard 生成全部字段。
- 安全测试：把 YApi 已公开的 RCE 攻击请求原样发过来，ApiYard 不会执行任何代码。✅ 全局 Mock 脚本里的沙箱逃逸、占位符参数里的代码都有测试；另外给 Mock 响应加了 CSP sandbox，防止借 Mock 地址做存储型 XSS。

## M7 MCP Server（v0.2，2.5–3.5 周）

**目标**：AI 编程工具（Claude Code、Cursor、VS Code、Codex 等）不用装任何插件，直接连上 ApiYard 查接口、写接口。现有的 Yapi-MCP 要另外装 Node 包、每个项目配一个 token，只能读写单个接口；ApiYard 内置在服务端，并多做 Mock 示例和 OpenAPI 导入导出。

### 设计决定

| # | 决定 | 原因 |
|---|---|---|
| 1 | **内置在服务端**，地址 `/mcp`，传输方式用 Streamable HTTP。客户端只需填地址和 token | 保持单文件部署；主流客户端都支持远程 HTTP 的 MCP Server |
| 2 | 用官方 Go SDK（`modelcontextprotocol/go-sdk`，目前 v1.8），按无状态模式运行，同时支持 `2025-11-25` 和 `2026-07-28` 两个协议版本 | 规范一年改了几版（2026-07-28 去掉了会话和 initialize 握手），自己实现跟不上；SDK 是纯 Go，新增的依赖不多。无状态模式不在服务端保存会话，重启和多实例都不受影响 |
| 3 | **鉴权沿用开放 API 的项目 token**：`Authorization: Bearer <token>`，多个项目用逗号分隔多个 token。权限按 token 所属的用户计算，和开放 API 完全一致 | 用户已经会在“项目设置 → token 配置”里拿 token，不用新建账号体系；MCP 能做的事不超过开放 API 已经允许的范围。暂不做 OAuth（要实现授权服务器，现在用请求头传 token 的客户端都支持） |
| 4 | 工具直接调用 `internal/api` 里的同一套逻辑（权限检查、参数校验、自动添加 tag、写动态），不经过 HTTP 绕一圈 | 行为和界面、开放 API 一致，不会出现两套规则 |
| 5 | 写入默认开启，服务端可以用 `-mcp off` / `-mcp readonly` 关闭；**不提供删除工具**；通过 MCP 写入的动态会注明“通过 MCP” | 拿到 token 本来就能通过开放 API 写入，默认关闭意义不大；删除容易被误触发，留给人在界面上做；写入能追溯 |
| 6 | 返回给模型的内容精简：去掉界面专用的字段（`__v`、`edit_uid`、`index` 等），`req_body_other`、`res_body` 里的 JSON 字符串解析成对象 | 减少 token 消耗，模型不用处理多层转义 |

### 工具

| 工具 | 类型 | 说明 |
|---|---|---|
| `list_projects` | 读 | token 能访问的项目：ID、名称、基础路径、描述、接口数 |
| `list_categories` | 读 | 项目的分类和每个分类的接口数 |
| `find_interfaces` | 读 | 按项目、分类、关键词（标题和路径）、状态、tag 查接口，返回摘要（ID、方法、路径、标题、状态），分页 |
| `get_interface` | 读 | 接口的完整定义（参数、请求体、响应），附带 Mock 地址 |
| `mock_example` | 读 | 用 Mock 服务的同一套逻辑生成一份示例响应，不发网络请求 |
| `export_openapi` | 读 | 把项目或某个分类导出为 Swagger 2 |
| `add_category` | 写 | 新建分类 |
| `save_interface` | 写 | 不传 ID 时新建，传 ID 时只修改给出的字段；路径冲突、分类不属于该项目时报错，规则与界面相同 |
| `import_openapi` | 写 | 导入 OpenAPI 3 / Swagger 2 文档（例如让 AI 从代码生成后直接导入），合并方式与界面的“数据导入”相同，默认跳过已有接口 |

工具都带上 MCP 的只读、幂等等标注，客户端可以据此决定是否需要用户确认。

**验收标准**：
- Claude Code 和另一个客户端（Cursor 或 VS Code）通过 HTTP 连上，用自然语言完成三件事：找到某个接口并说明它的参数；根据一段代码新增接口，界面上能看到接口和动态；导入一份 OpenAPI 文档。
- token 之外的项目一律看不到；token 所属用户权限不够时写入被拒绝；`-mcp readonly` 时写工具不出现在工具列表里，`-mcp off` 时 `/mcp` 返回 404。
- `2025-11-25` 和 `2026-07-28` 两个协议版本的客户端都能使用。
- Yapi-MCP 的 5 个工具能做的事，ApiYard 都能做到。
- 现有的兼容测试、生态测试全部通过。

- 个人访问令牌（一个 token 访问自己有权限的全部项目）：配置起来比逐个项目填 token 方便，但要新增数据表和设置页面。先用项目 token，看反馈再决定。

## 风险与决策点

| 风险 | 何时决定 | 应对 |
|---|---|---|
| 预构建前端无法单独使用 | M0.5 结束 | 转向重写精简前端，路线图重排 |
| YApi 的密码哈希或 Cookie 机制难以兼容 | M1 开始时 | 读源码确认；如果实在无法兼容，迁移后让用户重置密码 |
| ApiMind 先发布 | 暂不联系 | 在差异化上加码（单文件、SQLite、安全） |
| 业余时间不够，进度拖延 | 每个里程碑结束时 | 砍范围，不砍质量；可以把 M4、M5 推到 v0.1 之后 |
| 项目公开后被 issue 淹没 | M2 公开时 | 提供 issue 模板；README 写清楚"不做什么" |
