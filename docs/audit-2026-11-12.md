# ApiYard 项目审计与评估

日期：2026-11-12。基线：`main` / `5b759aa`，包含当前尚未提交的 M7 工作树改动。

## 结论

项目已形成可用的 v0.1 产品骨架：单文件部署、SQLite 存储、YApi 兼容场景、迁移、Mock、发布流水线均有实现与测试。架构方向适合轻量团队自托管，兼容性验证也明显强于只有普通单元测试的重写项目。

当前最需要补齐的是授权一致性和资源预算。审计确认了三条可复现的越权路径；Mock 生成存在高置信度的资源耗尽风险。建议先安排一次安全修复迭代，再继续扩大 MCP 写入能力。当前适合受控团队的开发预览；在修复以下 P1 前，不建议扩大为开放注册的多团队部署。

共记录 7 项问题：4 项 P1、3 项 P2。P1 表示应优先修复，P2 表示应纳入近期工程改进；没有将未验证的风险写成已利用漏洞。

## 问题清单

### A1 / P1：角色查询接口泄露私有项目完整配置

位置：`internal/api/profile.go:222`，尤其是 `projectFullDoc` 调用（230 行）。

`userProject` 在 `type=interface` 分支检查了私有项目权限，但直接指定 `type=project` 时没有查看权限检查，就返回项目完整文档及分组信息。项目文档含 `env`、前后置脚本和成员列表。公开注册默认开启，任意注册用户可枚举项目 ID。

隔离复现：同一名分组外用户调用 `/api/project/get?id=P` 得到 `errcode=406`；调用 `/api/user/project?type=project&id=P` 得到 `errcode=0`，包含 `env` 和 `members`。

建议：先对最终目标项目统一做可见性判断，再构建完整文档；同时审查直接 `type=group` 的个人空间数据。增加“同一对象所有读取路径均拒绝”的权限矩阵用例。

### A2 / P1：分组动态绕过私有项目的日志权限

位置：`internal/api/log.go:56`，`ListGroupLogs` 调用在 66 行。

`type=project` 检查私有项目查看权限；`type=group` 则把组内全部项目 ID 传入查询，没有检查调用者是否有权查看对应项目。返回的日志 `data` 包含接口更新前后的完整定义。

隔离复现：分组外用户查询项目动态得到 `406`，查询所属分组动态得到 `0`，能读取接口更新日志中 `current.res_body` 的测试标记。

建议：聚合动态只查询调用者可见的项目，并给分组自身动态定义访问策略。不要仅在顶层页面隐藏入口。

### A3 / P1：默认开放 API 加密口令允许改写 token 的用户身份

位置：`internal/api/openapi_auth.go:58`、85 行；`internal/yapitoken/yapitoken.go:25`；`internal/config/config.go` 的 token-salt 默认值。

项目 token 中的 `uid|rawToken` 用公开默认口令 `abcde` 加密，认证端根据其中的 uid 读取用户并授予其角色。持有正常开发者 token 的人可解出原始项目 token，改成站点管理员 uid 后重新编码。已有的“原始项目 token 必须存在”检查无法阻止这一情况。

隔离复现：正常开发者 token 调用 `/api/project/up` 得到 `405`；保留同一原始项目 token、仅改写 uid 后，同一操作得到 `0`。影响被项目 scope 限制在该 token 所属项目，不能据此声称已经取得全站管理员会话。

建议：新安装生成并持久化随机服务密钥；设计有完整性认证且可绑定签发身份、权限范围的新版 token。迁移兼容 token 应有明确的兼容开关或更严格权限策略。仅替换默认口令不足以完成新版 token 设计。

相关设计债：`canWrite` 对项目 token 刻意跳过角色检查。M7 文档中的“权限按 token 所属用户计算”不能直接由这套规则保证，MCP 接入前需先明确兼容 API 与 MCP 的权限契约。

### A4 / P1：Mock 生成缺少总量预算，可放大成进程级内存耗尽

位置：`internal/schemafake/schemafake.go:233`、329–342 行；`internal/mockjs/handler.go:148`。

Schema 的 `minItems/maxItems` 直接参与容量分配和循环；字符串长度、Mock.js 重复次数也没有输出预算。`maxDepth=20` 只限制深度，不能限制单层宽度或多层乘法放大。生成过程没有 context 取消检查；HTTP 层的小请求体限制不能约束生成结果。

小规模验证：一个很小的 Schema 可生成 10,001 个元素，未触发任何预算或上限。未在共享服务器执行大规模 OOM 攻击；进程级影响来自未受限分配路径的源码分析。

默认允许注册的用户可以创建项目和接口，保存放大模板后再调用公开 Mock 路由。恶意导入的 Schema 也能成为触发条件。

建议：对每次生成设置共享的最大节点数、数组长度、字符串长度、输出字节数及并发配额；在递归和循环中检查 context。超额返回受控错误。仅添加 HTTP 超时不能中断当前无 context 的生成循环。

### A5 / P2：迁移最终替换存在旧库丢失窗口，临时路径也不唯一

位置：`internal/migrate/migrate.go:62`、90–93 行。

迁移写临时库并核对是正确方向，但最终先 `removeDB(opt.Target)`，再 `os.Rename(tmp, opt.Target)`。删除成功后若进程中断或 Rename 失败，旧库已丢失；这不符合注释中“中途失败不会留下半成品”的强保证。固定的 `.migrating` 路径还会让两个相同目标的迁移互相删除临时库。

证据级别：源码确认，未对真实数据库制造中断。现有迁移测试覆盖正常覆盖与重复执行，没有覆盖替换阶段故障。

建议：使用目标目录中的唯一临时文件和排他锁；设计跨平台替换与回滚过程，保证失败时至少保留旧库或可恢复备份；补充 Rename/权限/并发故障测试，并明确迁移前必须停止服务。

### A6 / P2：压缩库命中已公布漏洞范围，缺少持续依赖检查

位置：`go.mod` 中 `github.com/klauspost/compress v1.16.7`。

官方 [GO-2026-6865](https://pkg.go.dev/vuln/GO-2026-6865) 列出 `fse` 和 `huff0` 的问题，修复版本为 v1.20.2。项目可执行程序确实引入 `fse/huff0/zstd`，MongoDB 驱动使用 zstd，源码中的解压链调用 `huff0.ReadTable`。

这条依赖主要服务 MongoDB 迁移；是否实际触发取决于压缩协商及输入，不能直接等同于普通 Web 请求即可利用。另一个命中版本范围的 [GO-2026-5841](https://pkg.go.dev/vuln/GO-2026-5841) 针对 `s2.NewDict`，当前检查到的可执行依赖列表没有 s2，应与实际可达问题区分。

建议：升级压缩库并验证迁移兼容性，在 CI 加入 govulncheck；同时生成发布制品 SBOM。依赖升级应验证调用链，不把“版本命中”全部作为可利用漏洞。

### A7 / P2：镜像发布没有受测试任务成功约束

位置：`.github/workflows/release.yml:38`、63 行。

`binaries` 运行测试后创建 Release 草稿，但 `image` 是独立任务，没有 `needs` 测试门禁，直接推送正式版本与次版本镜像标签。因而测试失败时，镜像仍可能发布并更新可被部署端拉取的标签。

建议：抽出共同验证任务，让二进制与镜像发布都依赖它；同时记录构建来源和制品摘要。此问题由工作流依赖图确认，本次没有触发真实发布。

## M7 进度校准

- 已实现：SDK 依赖、无状态 HTTP 路由、Bearer token 有效性检查、模式配置。
- 尚未实现：9 个工具、业务方法抽取、读写模式对工具暴露的约束、MCP 写入来源动态、使用文档、工具级权限测试。
- 当前 `AuthenticateMCP` 只返回项目 ID，HTTP 层还丢弃了返回值，没有保存每个项目对应的用户身份。工具实现前应引入明确的请求主体及项目授权上下文。
- 先前的 HTTP 探针只断言 initialize 响应状态为 200，没有断言响应 payload 中的协商版本，也没有使用 Claude Code 与第二个实际客户端。因此 M7 第 1 项应记为“基础实现完成、验收未完成”，不能记为全部完成。
- v0.1 的发布完成与产品安全成熟度是两个不同指标。README 的“开发预览”定位与当前证据相符。

## 建议执行顺序

1. 暂缓增加 MCP 写工具，先修复 A1/A2；建立私有项目跨接口、跨聚合路径的权限矩阵。
2. 修复 A3，明确旧 token、新 token 和 MCP 的权限契约，再抽取共享业务方法。
3. 给生成器增加统一资源预算（A4），补超额和取消测试。
4. 修复迁移替换过程（A5），用故障注入验证旧库可恢复；更新压缩依赖与发布门禁（A6/A7）。
5. 继续 M7：先读工具，再写工具，最后完成真实客户端与权限隔离验收。

后续安全债包括：新账号及改密改用慢密码哈希、迁移账号登录后渐进升级；登录/注册限速；请求体读取期限；浏览器回归；持续依赖扫描。本次不把这些设计改进计入上述 7 项已定位问题。
